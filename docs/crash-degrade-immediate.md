# 策略「立刻降级」验证：**失败**（短抖动仍 5/5 崩 + 长抖动降级风暴）

## 结论（第一句）

把阈值降到 500ms 后：**极短抖动 5 轮仍然崩 5 次**（该阶段 degrade-handoff 一次都没触发）；
**长断开 3 轮不崩，但降级风暴**（15 次 handoff，其中 5 次在 1 秒内连发），且风暴后**区块行数掉到 0（页面半死）**。
按你的验收标准，**这个方案不可行**，立即上报。

## 1. 原始数据（同一次运行，两阶段）

    18:22:09 PHASE1 short begin  → 18:24:42 PHASE1 end    (0.6s 断开 x5)
    18:24:47 PHASE2 long  begin  → 18:26:17 PHASE2 end    (5s blackhole x3)
    RENDER_GONE #1..#5  10:22:2x / 10:22:55 / 10:23:26 / 10:23:57 / 10:24:28  (exitCode:5)
    timeup crashes=5

阶段归属：**5 次崩溃全部落在 PHASE1（短抖动）**；PHASE2（长断开）**0 崩溃**。

## 2. PHASE1（短抖动）为什么没走降级

PHASE1 期间 degrade-handoff **0 次**。原因：0.6s 抖动下，远端腿的 close 之后约 200ms 就重新 open，
而降级判定只在「失败事件到达」时求值；重新 open 会立即把 unavailableSince 清零，
**时钟永远攒不到 500ms** → 永不降级 → 仍走那条不可靠的自研重连链 → 5/5 崩。

## 3. PHASE2（长断开）：不崩，但降级风暴

degrade-handoff 共 **15 次**，且呈爆发式：

    18:24:48.365 {"unavailableMs":629}
    18:24:49.382 {"unavailableMs":619}
    18:24:50.359 {"unavailableMs":635}
    18:24:51.344 {"unavailableMs":619}
    18:24:52.352 {"unavailableMs":619}
    18:25:18.505 {"unavailableMs":623}  ...

即「交还 → 页面重连 → 新 router 立刻发现腿仍不可用 → 0.6s 后再交还」的**自激循环**（约 5 次/秒）。
这正是你担心的二次伤害。

## 4. 页面可用性（关键否决项）

风暴结束后采样：

    {"composer":1,"rows":0,"nodes":2485,"block":1,"boots":2}   (连续多次)

- composer 存在（1）、节点数正常（2485）、区块挂载（block=1）；
- **但 rows=0**：区块里**一条会话都没有** → 远端数据没有恢复；
- boots=2（PHASE1 崩过一次并重载）。

按你的判据「交还后无法自行恢复（页面永久半死）→ 方案不可行」，**这里就是半死**：
交还风暴让页面反复重连，但远端数据始终没回来，区块空着。

## 5. 结论与建议

1. **「立刻降级」不可行**：它治不了短抖动（时钟被快速重连清零，降级不触发），
   却让长断开变成降级风暴，并把页面留在「区块空」的半死状态；
2. 阈值不是关键变量 —— 3.5s 与 0.5s 两版都试过，短抖动都崩；
3. 真正的病灶仍在自研重连链（上一轮已证明 attempt 的 onOpen 从不执行、remote-open 从不出现），
   **只有修好它才能同时解决短/长抖动**；
4. 建议把本轮三条诊断打点（reconnect-enter / attempt-run / attempt-early-return）留着，
   下一轮用它定位「attempt 是否被调用、被谁提前 return」，而不是继续调阈值。
